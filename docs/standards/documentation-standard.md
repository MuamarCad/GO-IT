# Стандарт документации

**Статус:** Действует
**Владелец:** Tech Lead
**Обновлено:** 2026-11-13

Документация проекта живёт в репозитории рядом с кодом, проверяется теми же командами и обновляется в тех же изменениях. Этот документ задаёт, какие бывают документы, где они лежат, как заполняются и что проверяет автоматика. Шаблоны лежат в [docs/templates](../templates/README.md).

## 1. Принципы

1. **Документация как код.** Документ меняется в том же коммите, что и поведение, которое он описывает. Правки проходят ревью.
2. **Один источник правды.** Каждый факт описан в одном месте, остальные документы ссылаются на него. Копировать таблицы маршрутов, моделей и чисел нельзя.
3. **Утверждение подтверждается запуском.** Число, статус «готово» или «проходит» попадает в документ только из реального запуска (см. §8).
4. **Документ имеет владельца и дату.** Без владельца документ устаревает первым.
5. **Короткий документ лучше длинного.** Если раздел никто не читает, его удаляют. История сохраняется в Git.

## 2. Типы документов

| Тип | Вопрос читателя | Примеры | Шаблон |
|-----|-----------------|---------|--------|
| Справочник (reference) | «Что именно есть?» | Спецификация, глоссарий, формат контента | [document](../templates/document.md) |
| Объяснение (explanation) | «Почему так устроено?» | Архитектура, дизайн-система | [document](../templates/document.md) |
| Инструкция (how-to) | «Как это сделать?» | Разработка, тестирование, руководство по контенту | [document](../templates/document.md) |
| Эксплуатация | «Что делать, когда сломалось?» | Runbook | [runbook](../templates/runbook.md) |
| Запись решения | «Почему выбрали это?» | ADR, RFC | [adr](../templates/adr.md), [rfc](../templates/rfc.md) |
| Запись качества | «Что нашли и что сделали?» | Аудит, постмортем, тест-план | [audit-report](../templates/audit-report.md), [postmortem](../templates/postmortem.md), [test-plan](../templates/test-plan.md) |
| Вход требования | «Что просит заказчик?» | Журнал требований | [requirement](../templates/requirement.md) |

Тип определяет форму. Не смешивайте: инструкция не объясняет историю решения, а ADR не содержит пошаговых команд.

## 3. Структура репозитория

```
README.md          вход в проект (не больше 80 строк)
CONTRIBUTING.md    как вносить изменения
SECURITY.md        модель угроз и ограничения
CHANGELOG.md       что изменилось и когда
GIGACODE.md        контекст и правила для AI-агента
docs/
  README.md        индекс всей документации
  product/         спецификация, журнал требований заказчика
  architecture/    обзор архитектуры, adr/ (записи решений)
  design/          дизайн-система, бренд-бук
  engineering/     разработка, тестирование, руководство по контенту, runbook
  planning/        дорожная карта и технический долг
  quality/         audits/, postmortems/
  rfc/             предложения, ещё не принятые решения
  standards/       этот стандарт, глоссарий
  templates/       шаблоны документов
draft/             исходные макеты и презентации (не документация)
```

Правила размещения: новый документ создаётся в папке своего типа и добавляется в [индекс](../README.md); документ вне `docs/` допустим только из списка выше.

## 4. Имена файлов

- Только строчные латинские буквы, цифры и дефисы: `development.md`, `documentation-standard.md`.
- Исключения: `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG.md`, `GIGACODE.md`.
- ADR: `NNNN-краткое-название.md` (четыре цифры, нумерация сквозная, номер не переиспользуется), например `0004-sessions-in-memory.md`.
- RFC: папка `NNNN-название/` с `README.md` внутри и приложениями рядом.
- Аудиты и постмортемы: `ГГГГ-ММ-ДД-название.md` по дате события.

## 5. Заголовок документа

Первая строка файла — заголовок первого уровня (один на файл), затем блок метаданных, затем пустая строка и текст:

```markdown
# Название документа

**Статус:** Действует
**Владелец:** Tech Lead
**Обновлено:** 2026-11-13
```

| Поле | Значения |
|------|----------|
| Статус | см. таблицу ниже |
| Владелец | `Tech Lead`, `Системный аналитик`, `Backend`, `Frontend`, `QA`, `Продуктовый дизайнер` или `Команда` |
| Обновлено | дата последнего содержательного изменения, `ГГГГ-ММ-ДД` |

Допустимые статусы зависят от типа документа:

| Где лежит | Статусы |
|-----------|---------|
| ADR (`architecture/adr/`) | `Предложен`, `Принят`, `Заменён`, `Отклонён`. Дополнительное поле `**Дата решения:**` |
| RFC (`rfc/`) | `Обсуждается`, `Принят`, `Отложен`, `Отклонён` |
| Аудиты и постмортемы (`quality/`) | `Открыт`, `Закрыт` |
| Остальные документы | `Черновик`, `Действует`, `Устарел`, `Архив` |

`CHANGELOG.md` и шаблоны блока метаданных не имеют.

### Жизненный цикл

`Черновик` → `Действует` → `Устарел` (поведение изменилось, документ ещё не переписан, в начале ставится ссылка на замену) → `Архив` или удаление. Удалённый документ записывается в [таблицу перемещений](../README.md#перемещённые-и-удалённые-документы), история остаётся в Git. Документ, который никто не откроет и который не нужен для решения, удаляется, а не архивируется.

## 6. Что и когда обновлять

| Изменение | Обновить |
|-----------|----------|
| Новый или изменённый маршрут, форма, роль | [Спецификация](../product/specification.md) (§8 проверяется тестом) |
| Новая зависимость, пакет, слой, поток данных | [Обзор архитектуры](../architecture/overview.md) |
| Значимое техническое решение, замена решения | Новый ADR, старый получает статус `Заменён` |
| Крупное изменение, которое нужно обсудить до кода | RFC |
| Переменная окружения, команда запуска | [Разработка](../engineering/development.md), [README](../../README.md) |
| Изменение, видимое оператору (логи, порты, здоровье, ошибки) | [Runbook](../engineering/runbook.md) |
| Новый кейс, roadmap, статья, ментор | [Руководство по контенту](../engineering/content-guide.md), если меняется формат |
| Цвета, шрифты, компоненты, темы | [Дизайн-система](../design/design-system.md) |
| Замечание заказчика | [Журнал требований](../product/requirements-log.md) |
| Найденный дефект по результатам аудита | Новый документ в `quality/audits/` |
| Сбой, потеря времени или данных | Постмортем в `quality/postmortems/` |
| Любое изменение, заметное пользователю или команде | [CHANGELOG](../../CHANGELOG.md) |
| Новый термин | [Глоссарий](glossary.md) |

## 7. Правила письма

- Язык: русский. Названия кода, команд и файлов остаются как в коде. Английские термины даются при первом употреблении вместе с пояснением или ссылкой на глоссарий.
- Короткие предложения, активный залог, настоящее время: «сервер отвечает 303», а не «будет осуществлён редирект».
- Один абзац — одна мысль. Таблица — для сравнения, список — для шагов или перечислений, код — в блоке с указанием языка.
- Без оценочных слов («быстро», «надёжно») без цифры. Без маркетинга.
- Команда или значение, которое пользователь должен скопировать, приводится в блоке кода целиком и работает как написано.
- Ссылка вместо копии: на файл — относительным путём, на раздел — якорем.
- Диаграммы — Mermaid в блоке кода, чтобы они хранились как текст и попадали в ревью.
- Секреты, пароли и персональные данные в документах запрещены. Примеры значений помечаются как примеры.
- Даты: `ГГГГ-ММ-ДД`. Числа с единицами: `1 МиБ`, `15 с`.

## 8. Правило подтверждения статусов

Статус «выполнено» и числовое утверждение допустимы, только если выполнены все условия:

1. Есть тест, который проходит функцию так, как её проходит пользователь: открывает страницу и проверяет ответ целиком, а не только редирект или наличие маршрута.
2. Для замечаний заказчика проверен результат, о котором шла речь (страница открывается, иконка видна, текст на месте), а не факт изменения кода.
3. Числа (тесты, покрытие, маршруты, вопросы, темы) взяты из запуска. Маршруты в спецификации сверяет тест `TestSpecificationListsEveryRoute`.

Если проверить нельзя (нет браузера, нет БД), в документе записывается, что именно не проверено. Причина правила описана в [аудите 2026-11-11](../quality/audits/2026-11-11-audit.md).

## 9. Записи решений: когда ADR, когда RFC

- **ADR** (Architecture Decision Record) фиксирует уже принятое решение: контекст, выбор, альтернативы, последствия. Пишется, когда решение трудно отменить, затрагивает несколько пакетов или о нём будут спрашивать. Один ADR — одно решение. Принятый ADR не переписывается: при смене решения создаётся новый ADR, старый получает статус `Заменён` со ссылкой на новый.
- **RFC** (Request for Comments) нужен до реализации, когда решение спорное, дорогое или влияет на требования. Содержит мотивацию, предложение, альтернативы, риски и критерии принятия. Принятый RFC порождает ADR и задачи; отклонённый и отложенный остаются в `rfc/` как память о причинах.
- Мелкие решения (имя функции, стиль) в ADR не попадают.

## 10. Автоматические проверки

Проверки запускаются командой `make docs-check` (это `go test ./internal/docscheck`) и входят в `go test ./...`. Они проверяют:

| Правило | Что проверяется |
|---------|-----------------|
| Заголовок | Первая строка — `# …`, заголовок первого уровня один |
| Метаданные | `Статус`, `Владелец`, `Обновлено` есть, значения из допустимых списков, дата в формате `ГГГГ-ММ-ДД`, у ADR есть `Дата решения` |
| Ссылки | Относительные ссылки ведут на существующие файлы, якоря `#…` существуют |
| Индекс | Каждый документ из `docs/` перечислен в [индексе](../README.md), ADR — в [индексе ADR](../architecture/adr/README.md), шаблоны — в [каталоге шаблонов](../templates/README.md) |
| README | Не больше 80 строк |
| ADR | Имя `NNNN-название.md`, номера без пропусков и повторов |
| Устаревшие имена | В действующих документах нет упоминаний удалённых файлов и старой схемы «Версия/Дата» |
| Спецификация | Маршруты в §8 совпадают с `router.go` в обе стороны |

Проверка не оценивает качество текста: это задача ревью.

## 11. Ревью документации

Перед слиянием изменения с документами ревьюер проверяет:

- [ ] Документ нужен, тип выбран верно, дубликатов нет
- [ ] Метаданные заполнены, владелец назначен
- [ ] Числа и команды проверены запуском (§8)
- [ ] Связанные документы обновлены (таблица §6)
- [ ] `make docs-check` проходит

# Участие в разработке

**Статус:** Действует
**Владелец:** Tech Lead
**Обновлено:** 2026-11-13

Как вносить изменения в GO-IT: ветки, коммиты, проверки, ревью. Как запустить проект — в [руководстве разработчика](docs/engineering/development.md).

## Рабочий процесс

1. Создайте ветку от основной: `feat/<кратко>`, `fix/<кратко>`, `docs/<кратко>` (например `fix/audit-2026-11-11`).
2. Вносите изменения небольшими коммитами. Код, тесты и документы, которые связаны, лежат в одном изменении.
3. Перед отправкой пройдите [Definition of Done](#definition-of-done).
4. Откройте запрос на слияние по [шаблону](docs/templates/pull-request.md). Слияние — после ревью.

## Коммиты

Формат: `тип(область): краткое описание` (Conventional Commits), описание на русском, заголовок до 72 символов.

| Тип | Когда |
|-----|-------|
| `feat` | Новая возможность |
| `fix` | Исправление дефекта |
| `docs` | Только документация |
| `refactor` | Изменение структуры без изменения поведения |
| `test` | Только тесты |
| `chore` | Сборка, зависимости, служебные файлы |

В теле коммита: что и почему (не пересказ диффа), ссылка на требование, дефект или ADR, что не проверено.

## Definition of Done

Изменение готово, когда выполнены все пункты:

- [ ] `gofmt -l .` ничего не выводит, `go vet ./...` чистый
- [ ] `go test ./...` проходит (включает `make docs-check`)
- [ ] Страницы, которых касается изменение, открыты тестом, а для интерфейса и вручную в браузере
- [ ] Новое поведение покрыто тестом, дефекты закрыты тестом, который их воспроизводит
- [ ] Документы обновлены по [таблице стандарта](docs/standards/documentation-standard.md#6-что-и-когда-обновлять)
- [ ] Запись добавлена в [CHANGELOG](CHANGELOG.md), если изменение видно пользователю или команде
- [ ] Секреты и `.env` не попали в коммит

## Правила кода

- `gofmt` обязателен. Пакеты зависят друг от друга сверху вниз ([архитектура](docs/architecture/overview.md)).
- Данные, которые приходят от пользователя, проверяются на сервере; вывод экранируется (`html/template`).
- Формы, меняющие состояние, содержат CSRF-токен и завершаются редиректом или ответом 422.
- Шаблоны: внутри `range` используйте `$` для данных страницы; не добавляйте inline-скрипты.
- Ошибки не раскрывают внутренности (SQL, пути, стек).

## Ревью

Ревьюер проверяет: решает ли изменение заявленную задачу; есть ли тесты и проходят ли они; соответствуют ли документы коду; нет ли новых зависимостей без причины; нужно ли оформить ADR. Для документации — [чек-лист стандарта](docs/standards/documentation-standard.md#11-ревью-документации).

## Принятие решений

- Значимое решение, которое трудно отменить, фиксируется в [ADR](docs/architecture/adr/README.md).
- Спорное или дорогое изменение сначала оформляется как [RFC](docs/templates/rfc.md) и обсуждается.
- Замечания заказчика заносятся в [журнал требований](docs/product/requirements-log.md).

## Работа с AI-агентами

Правила для агентов описаны в [GIGACODE.md](GIGACODE.md). Статус «готово», который выставил агент, проверяется тестами и ревью так же, как работа человека ([правило подтверждения](docs/standards/documentation-standard.md#8-правило-подтверждения-статусов)).
